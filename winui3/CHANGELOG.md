## v2.0 — 多会话通道（2026-09-27）

远程会话从「单通道 + 系统 `mstsc` 窗口」重构为**多条会话通道并行执行 + 原生内嵌画面**。

### Added

**会话通道**

- **通道模型**：一条通道 = 目标主机 + 目标账户 + 凭据 + 指令桥目录 + 画面实例 + 运行状态。
  通道管理页支持新建 / 复制 / 删除 / 改名，以及逐通道的预检。
- **任务分配**：任务的 `channel_id` 决定它走哪条通道；下拉里「本地执行（当前会话）」是显式第一项，
  也是新建任务的默认值。通道之间**并行**、通道内部**串行**。
- **`RdpChannelSession`**：每通道一份运行时状态（指令归属、事件序号、进度、心跳、收尾幂等），
  判定链收敛成一个可单测的 `Tick()`。
- **启动计划**：`RdpChannelPlanner.Plan()` 分组 + 并发上限截断 + 跳过原因（纯函数，可单测）。
  指向不存在 / 已停用 / 没配账户的通道时**不执行**并说明原因，绝不静默改跑本地。
- **指令桥多实例化**：`RdpBridge` 从静态类改为实例类，按通道各持一份
  `command.json` / `status.json` / `stop.json`。
- **桥目录按账户名隔离**：`<ProgramData>\YukinoChan\rdp\<账户名>\`（见「升级注意」）。
- **凭据按「主机 + 账户」存**：同一主机的不同账户各存一条，互不覆盖；旧键保留回落读取。
- **停止覆盖全部通道**：`停止执行` / `紧急停止` 向每条通道各写一份 `stop.json`，
  代理在执行期间每秒检查并转成脚本引擎的停止请求。
- **并发上限 4 → 8**：原生 `YCN_MAX_SESSIONS` 提到 8（`ycn_rdp.c` 重编），
  C# 侧 `RdpNativeLimits.MaxSessions` 同步；超出上限的通道会被截断并**明示**（日志 + 一次对话框）。

**内嵌画面**

- 远程画面用原生 FreeRDP + D3D11 交换链**内嵌**在窗口里，鼠标键盘直接操作；
  `mstsc` 独立窗口模式保留为兜底。
- **全屏**：独立全屏窗口 + `WH_KEYBOARD_LL` 键盘接管（`Win` / `Alt+Tab` 转投远端），
  编排抽成 `RdpFullScreenCoordinator` 供管理页与通道页共用。
- **多画面同屏**：**全部通道** 2×2 网格、**每页 4 格**，超过则翻页；
  每格可「弹出窗口」变成普通可缩放窗口（关窗后画面自动回页面）。

**界面**

- 左侧菜单改为**两级**：「**会话通道**」是父项 —— 点它本身 = **多画面**（全部通道网格），
  其下子菜单才是各条通道单独的画面，末尾是「通道管理…」（配置 / 凭据 / 部署 / 预检）。
  子菜单按「配置里启用中的通道 + 本轮在跑的通道」实时重建，通道配好即出现（不必等到开始执行）。
- 通道画面页：通道头 + 该通道进度与心跳 + 画面区 + 该通道事件（可折叠，画面优先布局）。
- 任务页新增「执行通道」下拉，任务列表项显示所属通道。（**随后已改为按通道编排**，见下方 Changed）
- 主页新增「会话通道」概览卡（1Hz 快照刷新，点行跳转）。
- 状态面板（看板娘浮动卡 / 主页状态卡）改为整轮口径：
  单块 = 那一块，多块 = 整轮聚合（`执行中（N 块并行）`、墙钟耗时、进度求和）。

**收尾与反馈**

- 整轮汇总：日志 `[汇总] 共 N 块（本地 X / 通道 Y）：成功 …、异常 …。` + 逐块明细（异常块排前），
  只弹**一条**汇总通知；单块执行不发汇总。
- 看板娘改为在**整轮结束**时才定终态（取最差）——某条通道先跑完不会让它提前"休息"。
- 通道日志统一前缀 `[通道：<展示名>]`。

  - `ChannelsPage` 文案改「通道管理」，入口降为子项「通道管理…」（tag `channel-mgmt`）；

  - 「执行中的通道」分组标题连同那套平级插入逻辑一并删除；
  - 多画面列出的通道 = 配置里**启用中的** + 本轮在跑的（`SurfaceGridChannelIds`），

- 分辨率改为**按通道**配置；独立窗口模式的 `.rdp` 文件按通道分文件（`session-<id>.rdp`）。

### Fixed

- **`CompletionSignaled` 缺归属门禁**：上轮残留的 `done` 会让新指令秒判完成 ——
  现在完成 / 异常判定必须建立在"状态属于本轮指令"之上。
- **远程执行时「停止执行」按钮是灰的**（改造前远程模式全程 `IsRunning = false`，
  实际点不到停止）—— 现在远程 / 并行执行同样置位。
- **状态面板恒为空**：面板原先绑的四个属性只有本地执行会写，
  跑远程 / 并行任务时永远显示「空闲 / 00:00 / - / 0 / 0」—— 现统一走整轮口径的计算属性。
- **部署代理失败被误报成"需要管理员权限"**：真因是副本文件被常驻代理持有。
  现在按三档策略处理（原地覆盖 / 送走空闲旧代理 / 退到备用目录 `agent_b`），并给出准确归因。
- **画面被压成一条横带**：事件卡原先写死高度 —— 改为画面优先布局 + 事件卡可折叠。
- **通道页没有全屏入口**：全屏编排原先留在管理页 —— 抽成共用类后两页都能进，
  并加了"同时只允许一个全屏窗口"的守卫。
- **多账户并行时任务"跑完却被判异常"**：所有账户共用一份代理副本，日志与耗时统计都落在副本目录下，
  而 `ProgramData` 默认 ACL 只给 Users「读 + 建新文件」、文件归创建者所有 —— 一个账户建的
  `last_abnormal_report.json` / `runtime_history.json` / 同秒撞名的 `session_<时间戳>.json`，
  别的账户改不动，写统计直接抛异常并把整轮任务连坐判成异常。
  现在：**代理数据目录按账户分家**（`logs/<账户名>`、`runtime_stats/<账户名>`）、
  部署时给这两个目录放开 `BUILTIN\Users` 完全控制，且**统计写入失败只记日志、不再影响任务结果**。
- **「启动失败或提前退出」误判**：程序提权重启（典型是 BetterGI 未以管理员运行时用 `runas` 重启自己，
  原进程以退出码 553 秒退）或单实例转发，都会让直接进程立刻退出、由新进程接手。
  启动确认现在会开一个 10 秒**接力窗口**：监控目标出现或同名新进程在跑即判启动成功。
- **远程通道「停止执行」点了没用**（真机复现，见下方"停止链路"整段）：停止请求只在
  任务主循环的每秒计时回调里被检查，而收尾清理又同步堵在这个回调里 ——
  于是"点停止 → 界面卡住 → 代理那边迟迟不停"。现在停止检查独立成 500ms 并行循环，
  清理不再阻塞回传，主控端还会确认回执并自动补发。
- **设置页切主题 →「知道了」点不动、过一会儿整窗闪退**（真机复现）：`SelectionChanged` 里直接弹
  `ContentDialog`，而"改主题"会让 ComboBox 重新模板化并**二次触发** `SelectionChanged` ——
  同一个交互里连着两次 `ShowAsync`，第二次必抛 COMException `0x80000019`
  （*Only a single ContentDialog can be open at any time*）。异常落在 `_ = ...` 的
  fire-and-forget 调用里没人接，就成了未观察异常。现在三层收口：
  ① **所有** `ContentDialog` 一律走 `DialogHelper.ShowAsync()`（全局排队 + 异常就地落盘不抛）；
  ② 主题切换的反馈改成页面内一行文字（4 秒自动收起），不再弹模态框；
  ③ 对"值没变"的二次触发做幂等短路，不重复落盘、不重复提示。
- **「部署会话代理」点了像没反应，成没成只能猜**：成功分支原先只往运行日志追一行、改一个
  **通道页上根本不显示**的 `RdpStatusText` —— 而失败反而是弹窗的，一静一响正好把
  "部署好了"和"没点上"混成同一个体感（真机：22:24 那次其实成功了，日志里写着
  「已部署到所有用户共享启动目录…；已结束 1 个正在运行的旧会话代理」，用户只能来问）。
  现在成功也弹一次结果窗并说清后续动作，「移除代理」同样给回执；
  通道页在「开启远程桌面 / 部署 / 移除 / 重新检查」四个按钮下面补一行操作状态。
  另外判"要注销重连"不再只认「注销」二字 —— 日志里那句是「已结束 N 个…旧会话代理」，
  同样意味着新副本要等目标账户下次登录才启动。

### 停止链路（2026-09-27 二次修复）

真机复现记录：`rdp\zdh\status.json` 在点下「停止执行」后停在 `Phase=running` 再没更新，
日志停在「收到停止请求，正在收尾。」；`rdp\bh3\stop.json` 则从 12:26 一直躺到 15:00 没人消费。
据此定位到四个独立缺陷，一并修掉：

- **代理侧停止检查的位置错了**：原先挂在 `ScriptRunner` 的每秒计时回调上，而那个回调只在
  任务主循环里触发 —— 执行流程停在启动确认、接力确认、并发组等待、或正在做进程清理时，
  停止请求根本没人读。现在由一条与任务执行**并行**的 500ms 监听循环负责（`StartStopWatcher`），
  任何阶段都能在半秒内响应。
- **`ScriptRunner.RequestStop` 同步干重活**：整轮关键词清理要枚举全部进程并逐个 `taskkill`，
  实测十几秒（`bh3` 从停止到收尾隔了 14 秒），期间工作线程被占死，进度与心跳全部停摆 ——
  这就是"点了停止，界面像卡住"。现在请求只置标志位 + 立刻结束已登记的直接脚本进程，
  按关键词的统一三层清理改由 `RunCore` 的收口处 `CleanupForStop()` 执行。
  ⚠️ 这一步**不能只依赖任务主循环**：`ConfirmLaunchSuccess` / `TryConfirmRelayLaunch`
  一看到停止请求就返回 false，而那条分支原本只 `UntrackProcess` 不做任何清理 ——
  目标进程（含提权 / 单实例接力起来的新实例）会活下来，表现成"点了停止，游戏还在跑"。
  所以现在：那条分支在停止时**不解除登记**、也不记"启动失败"异常，直接把登记信息交给
  `RunCore` 收口处的统一收尾；清理范围按**已登记过的任务**（`_tasksByPid`）定，
  只覆盖真的启动过的那批，免得顺手杀掉只是关键词撞上的无关程序；紧急停止才扩大到全部任务配置。
  收尾必须在 `_currentProcesses.Clear()` **之前**跑，否则拿不到登记进程。
- **停止请求只发一次、发了不管**：代理漏读或版本过旧时，用户永远等不到任何反馈。
  现在主控端每 5 秒确认一次回执（代理把相位切成 `stopping` 或回"收到停止请求"的日志），
  没回执就补发（最多 5 次），到上限直接点名"目标代理多半是旧版本，请重新部署会话代理"。
  界面文案也固定成「已请求停止，等待目标会话确认…」，不再被代理回传的"运行中"盖回去。
- **`stop.json` 会残留**：执行期才检查停止，导致"点停止 → 又点紧急停止"时后一份永远没人收。
  现在代理收尾后清一次、空闲心跳分支顺手清一次、**主控端下发新指令时也清一次**。
- **关键词带 `.exe` 时清不掉游戏本体**：游戏的真实镜像名是英文（原神 = `YuanShen`、
  崩铁 = `StarRail`），按名字 `taskkill /IM "原神"` 注定打不中 —— **只剩"按窗口标题兜底"
  这一条路**能把游戏清掉，而窗口标题又不会带 `.exe`。原来拿原始关键词去比标题
  （「原神.exe」vs「原神」），这条路整个失效，表现成"停止了但游戏还在跑"。
  现在统一走 `ProcessHelper.TitleMatchKey()`：剥扩展名 + 大小写归一后再比标题与镜像名，
  `TerminateProcessesByWindowKeyword` 也带回退。
- **"结束了没有"完全看不出来**（真机再次踩到）：`taskkill` 的输出与退出码全被丢弃、
  异常也被吞，日志里只有"正在结束 X" —— 成功与失败长得一模一样。
  用户对着还在跑的游戏只能猜是"没杀掉"还是"画面没刷新"。现在：
  - `ProcessHelper.RunHidden` 把退出码与 stderr 带回来，`TerminateProcessName` /
    `TerminatePidTree` / 新增的 `TerminateProcessTree` 都返回 `ProcessTerminateResult`，
    失败会把 taskkill 的原始原因写进日志（顺带修掉"重定向了输出却不读"的死锁写法）；
  - 强杀被拒时**降级**：先换托管 API（异常信息比 taskkill 有信息量），
    再退到给目标窗口发 `WM_CLOSE`（应用层消息，反作弊驱动不拦，走游戏自己的退出流程）；
  - 清理末尾新增**复查**（`ReportCleanupResult`）：明确写"✓ 已复查确认任务相关的进程都已结束"
    或"⚠ 复查发现 N 项仍在运行：…"并给出下一步。
- **配置里写的是中文窗口标题，实际进程名是英文**：只按配置查，会同时踩"杀不掉"和
  "复查不出"两个坑。现在监控命中的那一刻会把该窗口所属进程的**真实镜像名**记下来
  （`LearnMonitorImageNames`），停止时按它清理与复查，不再依赖窗口是否存在。

> 升级提醒：这一版**必须重新部署会话代理**（代理代码变了），否则目标会话里跑的还是旧副本，
> 停止请求依旧不会被完整响应。

### 停止整棵进程树（2026-09-27 三次修复）

真机现象：**明明点了停止、任务也确实结束了，过一会目标会话又自己跑起来**。

复现记录（`bh3` 通道）：22:41:40 发出停止请求，22:41:47 结束掉脚本进程，22:42:01 日志打出
「✓ 已复查确认，任务相关的进程都已结束」；然而 22:42:57 目标会话里游戏被**重新启动**，
一路跑到 22:49:31 才收尾。事后查进程表，`March7th Assistant.exe`（PID 101176，父 PID = 被结束的
`March7th Launcher.exe`）**一直活着** —— 它才是真正干活的引擎，游戏正是它重新拉起来的。

根因有两层，缺一不可：

- **结束整棵树时把托管 API 的返回值当成了结论。** 任务配的 `March7th Launcher.exe` 只是个壳，
  真正干活的是它派生的 `March7th Assistant.exe`。停止时 `taskkill /IM /T /F` 被拒（拒绝访问），
  降级到 `Process.GetProcessById(pid).Kill(entireProcessTree: true)` —— 它**回报"结束成功"，
  却只带走了根 PID**；子进程发现游戏窗口没了，就自己 `游戏终止 → 游戏启动` 把游戏拉回来。
  现在 `ProcessHelper.TerminateProcessTree()` 改成五步，**任何结束动作之后都必须自己复查**：
  - **动手前**先用一次 Toolhelp32 快照（`NativeMethods` 新增 `CreateToolhelp32Snapshot` /
    `Process32FirstW` / `Process32NextW`）把整棵树记下来 —— 根进程一死，进程表里就只剩孤儿记录，
    那时再想按 PPID 补课已经晚了（这正是当初漏网的直接原因）。父子关系自己拿，
    也不受会话限制，能列到目标会话里的进程；
  - `taskkill` 先试一把；
  - **复查①**：不看退出码，只问"这些 PID 还在不在"；
  - 剩下的自己动手，**倒序遍历 = 从叶子往根**（先断掉会自己重启的引擎，最后才收壳）；
  - **复查②** 才给结论，失败就把「整树 N 个进程中仍有 M 个在运行：…」写进日志。
  `IsSameProcessAlive()` 还会比对镜像名，**防止 PID 被系统复用**后把无关的新进程误判成残留。
- **清理与复查用的名字不是同一套，复查因此打出了假的 ✓。** `BuildCleanupPlan` 只收
  `script_path` 的文件名和 `wait_process_name` —— 活下来的那个 `March7th Assistant.exe`
  **既不是脚本文件名、也不在 `wait_process_name` 里**，于是清理和复查两边都看不见它。
  现在：
  - **任务名**（经 `ProcessHelper.LooksLikeImageName()` 把关，避免把「原神日常」这类显示名
    当成进程名）纳入「启动脚本进程」阶段，清理与复查共用同一份计划；
  - 脚本进程**实际派生的后代**由 `ScriptRunner.LearnScriptDescendants()` 登记，
    `TerminateScriptDescendants()` 结束，`ReportCleanupResult` 按同一份名单复查。
    记的是 **PID 而不是名字** —— 脚本常会派生 `conhost.exe` 这类公共进程，
    按名字清会误伤系统里别的同名实例；
  - 学习时机放在**停止链路上最早的一刻**（`TerminateTrackedProcesses`，代价只是一次毫秒级快照）
    以及 `CleanupProcessesForTasks` 开头，并且**紧接着登记就收后代** —— 不给它
    "把游戏重新拉起来"的时间窗；
  - 复查若发现漏网的是**脚本自己的子进程**，会单独点名并提示它可能重新拉起游戏，
    不再和"游戏杀不掉"混在一句话里。

顺带修到的一处：`ProcessNamesForTask` 现在也包含任务名，于是「启动确认」阶段
"直接进程秒退 / 单实例转发"的**接力判定**能认出由启动器派生的引擎进程 ——
像 `March7th Launcher.exe` 这种"起完就退"的壳，以前会被误判成"启动失败或提前退出"。

升级提醒同上：这一版同样**必须重新部署会话代理 + 注销目标账户重连**。

### Upgrade notes

⚠️ **桥目录规则变更，升级后必须重新部署会话代理**

```text
旧：<ProgramData>\YukinoChan\rdp\
新：<ProgramData>\YukinoChan\rdp\<账户名>\
```

已部署过代理的机器，升级后**重新点一次「部署会话代理」**，然后**注销目标账户再重连**
（代理是账户登录时由启动项拉起的）。否则表现是"代理明明在跑，却一直显示不在线"。

其他：

- 旧配置自动迁移出一个默认通道并让任务指向它，**原来能跑的行为不变**；
- 代理部署成功后旧代理已被结束，同样需要注销目标账户再重连；
- 内嵌画面改用原生 FreeRDP，旧配置里的 `rdp.embed_remote_desktop` 键仅为兼容保留，读进来恒为 `false`。

### Known limitations

- 一次最多 8 条通道并行；多画面每页最多 4 格（8 路同时渲染开销不可接受）。
- 弹出到独立窗口的画面，只能从主窗口菜单「执行中的通道」再进页面找回来。
- 心跳宽限期上限 90 秒，因此 90 秒内的真断线最迟约 90 秒才告警（刻意折中）。
- 内嵌会话暂不支持剪贴板互通。
- 桥的 `command.json` / `status.json` 仍是 PascalCase，与 `config.json` 的 snake_case 约定不一致。
